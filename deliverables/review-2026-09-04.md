# local-sharing 整体审查与优化路线图

> 审查日期：2026-09-04 ｜ 方式：4 名成员并行只读审查 + 主理人交叉核实
> 审查范围：桌面端 `desktop/src`（~1900 行 TS/JS/CSS）、安卓端 `android`（~2500 行 Kotlin）、仓库工程状态、产品功能与体验
> **本轮只做分析，未修改任何源码**

---

## 〇、一句话结论

**功能骨架已经立住（双向传输、扫码、系统分享入口、活动历史都通了），但存在一条会随使用稳定劣化的功能性硬伤、一个几乎没画信任边界的安全面，以及一片空白的工程基建（测试 0%、~760MB 二进制裸奔、21 个改动未提交）。**

按健康度打分：**功能完整度 8 分 / 工程质量 5 分 / 安全 3 分 / 工程基建 2 分**。

## 一、P0 必修（已被多方独立命中 + 主理人已逐条核实）

### 1.1 大文件传输必然失败 —— 60 秒固定 ACK 超时 ⭐ 最高优先级

| 项 | 内容 |
|---|---|
| 位置 | `desktop/src/services/services.ts:20`（`const ACK_TIMEOUT_MS = 60_000`）、超时分支 `:382-392`、完成分支 `:401-411` |
| 主理人核实 | ✅ `services.ts:20` 确认硬编码 `60_000`；`:386`（超时）与 `:407`（收到 ACK）两处都调 `safeUnlink(t.filePath)` 删文件 |
| 后果 | 超时与文件大小**完全无关**。2GB 文件需 >33MB/s 才能跑完，普通 WiFi 远达不到 → 传输中被判失败并**删除源文件**；若手机正在下载，会得到**截断的坏文件**，且全仓无任何 md5/sha 校验（grep 为空） |
| 三方验证 | 架构师 P0-7、QA R1、产品经理均独立命中，结论一致 |
| 修复方向 | 超时改为随文件大小动态放大；或引入 `downloading` 心跳（`TransferStatus` 里已定义该状态但从未被赋值），收到首个 Range 请求后停止倒计时 |

### 1.2 桌面端"信任边界"几乎为零 —— 同一 WiFi 的任何人可读写删你的文件

根因是**整个服务假设「局域网 = 可信」**，以下 5 件事叠加：

| # | 位置 | 问题 |
|---|---|---|
| a | `config.ts:42` + `src-tauri/src/main.rs:52-55` | `shareCode` 默认空，且 Tauri 主进程**根本没注入 `SHARE_CODE`** → 打包版注册接口零门槛发 token |
| b | `app.ts:136-293` | 除 `POST /api/upload` 外，**所有 `/api/*` 无鉴权**：`DELETE /api/received`（删磁盘文件）、`POST /api/settings`（改保存目录）、`GET /api/received`（返回磁盘绝对路径）等全部裸奔 |
| c | `app.ts:97` | `app.use(cors())` 无参数 → `Access-Control-Allow-Origin: *`；无 Host/Origin 校验 → **DNS rebinding** 可绕过 SOP |
| d | `app.ts:191-209` | **先落盘、后鉴权**：multer 在第 192 行已写入磁盘，第 195 行才验证；401 时不做清理 → 未授权者也能写文件 |
| e | `app.ts:260-270` + `config.ts:140-146` | `POST /api/settings` 无鉴权 + `downloadDir` 只校验 `existsSync`，无根目录白名单 → 理论可写入自启动项 |

> **建议当成「一个引入信任边界的重构」整体做，而不是拆成 5 个补丁。** 另有一个设备劫持链（P0-6）：`GET /api/devices` 无鉴权拿到 deviceId → `POST /api/devices {clientId: 该id}` 即可轮换 token 顶替受害者。

### 1.3 安卓端主线程 IO → 选大文件夹 / 收大 zip 必 ANR

| # | 位置 | 问题 |
|---|---|---|
| P0-1 | `HomeScreen.kt:120`、`391-401` | `walkTree()` 对 SAF 树递归遍历，每进一层是一次 ContentResolver IPC。选一个 500+ 文件的相册目录 = 主线程 500~1000 次跨进程查询 |
| P0-2 | `ShareViewModel.kt:288` → `332-356` / `380-412` | `writeToTree` 是 `suspend` 但**没有 `withContext(Dispatchers.IO)`**；`extractZipToTree` 连 suspend 都不是 → 解压 zip 跑在 Main 线程。对比 `FileUtil.extractZip:99` 和 `zipUris:64` 都写了 IO 线程，说明是**遗漏而非有意** |

### 1.4 安卓端 Zip Slip 路径穿越 ⭐ 已由主理人核实

| 项 | 内容 |
|---|---|
| 位置 | `android/.../util/FileUtil.kt:105`（`val target = File(outDir, entry.name)`）、`ShareViewModel.kt:365`（`File(dir, transfer.name)`） |
| 主理人核实 | ✅ 两处均为裸路径拼接，**全仓 grep `canonicalPath` 无任何校验代码** |
| 后果 | 恶意/被控的局域网电脑可让手机把文件写到任意路径；且无解压条目数/总大小上限（zip bomb） |
| 修复成本 | **约 3 行**：`check(dest.canonicalPath.startsWith(outDir.canonicalPath))` + 条目数/字节数上限 |

### 1.5 安卓端 ViewModel 无 `onCleared` + 无异常兜底

| # | 位置 | 问题 |
|---|---|---|
| P0-3 | `ShareViewModel.kt:262-279`、`288-328` | 两处 `viewModelScope.launch` **无 try/catch 也无 CoroutineExceptionHandler** → 未捕获异常直接崩 App（触发点：`:375` copyTo 磁盘满、`:380` 解压失败） |
| P0-4 | `ShareViewModel.kt:39-593` | **全文缺少 `override fun onCleared()`** → WS 不 close（泄漏 + 后台持续重连）、`connectWs()` 重复调用产生孤儿连接 |
| P0-5 | `ShareViewModel.kt:514/572`、`HomeScreen.kt:123` | 分享进来的文件复制到 cacheDir 后**从不删除**；文件夹 zip 用不带时间戳的固定名会互相覆盖 |

### 1.6 其余已交叉验证的 P0

| # | 位置 | 问题 | 交叉验证 |
|---|---|---|---|
| 删除记录不落盘 | `services.ts:211-219` | `removeReceived` 只改内存未调 `persistAllActivity` → **重启后已删文件"复活"** | 架构师 P1-16 + QA R4 |
| zip 写失败请求永久挂起 | `services.ts:414-429` | `zipFiles` 只监听 `archive.on('error')`，**未监听 `output.on('error')`** → 磁盘满时 Promise 永不 settle，HTTP 请求永久挂起 | 架构师 P1-15 + QA R3 |
| 历史持久化 O(N²) | `services.ts:79-110` + `config.ts:126-131` | `persistAllActivity` 逐条 `appendHistory`，每次都是全量读-改-写 → 500 条历史时一次 ACK 触发 500 次同步文件读写，**同步阻塞事件循环** | 架构师 P1-8/-9/-10 |

## 四、已核实「不是问题」（避免浪费修复预算）

架构师特意验证过，**不要进路线图**：

| 被怀疑的点 | 核实结论 |
|---|---|
| zip 打包缓冲进内存 → GB 文件 OOM | ❌ 不成立。`services.ts:419-427` 是 `archiver.file()` + `pipe(createWriteStream)`，全程流式。真正代价是 CPU（`zlib level 9`）和 3× 磁盘 I/O |
| 上传文件名 `../` 路径穿越 | ❌ 不成立。`app.ts:55` 第一行就是 `path.basename()`，目录部分被丢弃 |
| zip slip（桌面端打包侧） | ❌ 不成立。服务端从不解压，只有打包 |
| token 随机性不足 | ❌ 不成立。`services.ts:26-28` 用 `crypto.randomBytes(16)` = 128 位 CSPRNG。问题在"谁能拿到 token"，不在强度 |
| 模块循环依赖 | ❌ 不成立。`ws.ts → services.ts → config.ts/types.ts` 单向，是 DAG |
| token 明文落盘（安卓） | ✅ 无风险。`Prefs` 只存 auto_save/last_base_url/save_tree_uri 等，**token 只在内存流转** |
| `GlobalScope` 泄漏 | ✅ 无。全仓 grep 确认无 `GlobalScope` 或裸 `CoroutineScope` |
| 两端空状态 | ✅ 做得好。`EmptyState` 组件 + 仪表盘三处空态都有图标+标题+引导语，不用返工 |

## 六、值得肯定的地方

- **踩过的坑都写成了注释**：`mNextRc` 越界、`ImageProxy` 必须关闭、分享 Uri 临时授权失效、ActivityResultContract 必须单例、native 崩溃靠 logcat 兜底 —— 这些是实战痕迹，不是 AI 生成的代码
- **躲过了两个最容易踩的 OOM 坑**：上传走 multer diskStorage 而非内存缓冲、zip 全程流式
- **中文文件名 latin1 还原**（`app.ts:40-51`）看得出是被真实设备毒打过的产物
- **状态管理基本正确**：安卓端全部 `MutableStateFlow` + `asStateFlow()` 双写模式，更新一律走 `update {}`，无裸 `.value = ` 竞态
- **两端空状态打磨到位**

一句话：**这是一个"能用但不敢托付大文件"的工具；补上第一批 7 条 + 第二批 4 条，就能从"差点意思"变成"愿意推荐给信任的人"。**
